# Validated checkpoints

Use this protocol when approved work has dependent increments or an uncertain integration boundary. Read the ticket/spec, relevant design decisions and the repository's delivery reference first. Its Definition of Done, verification scope, review limits and delivery authority remain authoritative.

1. **Baseline.** Establish the runnable baseline and remaining delta. Keep working behavior and its evidence available. Choose the smallest next increment whose result is independently observable through an agreed public boundary. Internal checkpoints may prove a capability needed by a complete ticket; they are not automatically separate tickets or deliverables.
2. **Plan.** Before implementing that increment, identify its completion criterion, focused proof and any authority or finite external-action budget it needs. Use the ticket's checkpoint plan; if missing, derive a compact plan from approved acceptance criteria. Resolve only decisions that cannot be inferred from existing agreements. Budget approval and execution permission are separate; a failed or ambiguous attempt does not replenish the budget.
3. **Prove.** Implement and verify the increment before building behavior that depends on it. Prefer public behavior and the actual integration boundary when that boundary carries uncertainty. Use the repository's declared verification scope and execution path. Record the tested revision/artifact, target and observed result; passing fixtures do not establish an untested live or installed boundary.
4. **Advance.** Advance autonomously when the criterion has passing evidence and the next increment remains within approved scope, permissions and budgets. A checkpoint is a proof boundary, not a request for human approval. Continue safe independent work while an external gate awaits its owner.
5. **Recover.** On failure, preserve the last proven checkpoint and its evidence. Diagnose and repair within scope while fresh evidence changes the hypothesis. Honor repository review/retry limits and the agreed finite budget for stateful or costly operations. Repeating an unchanged failure without new evidence, exhausting a budget, unresolved consequential choices, missing authority or unverifiable external state requires a handoff. Record the last proven revision/artifact and target, failed observation, current hypothesis, budget consumed/remaining where applicable, smallest next diagnostic, next owner and exact condition for resuming. Resume from the last proven checkpoint when that condition is met, then rerun the affected proof.

Existing capabilities are regression checks. Completion criteria for new behavior describe the remaining delta, rather than count an already working baseline as new delivery. Retain checkpoint evidence in the repository's existing work record so a later session can identify the last proven state and remaining work.

Report completion against acceptance criteria and the repository's Definition of Done. Distinguish applicable implementation, validation, installation, publication and enablement claims with their evidence; retain unknowns and remaining work explicitly. Reuse the repository's reporting convention. When no delivery reference exists, report the observed boundary and gap honestly; checkpoint planning does not create a competing delivery agreement.

## Foundations and ownership

This independently owned agent-workbench protocol adapts Matt Pocock's published [tracer bullets](https://www.aihero.dev/tracer-bullets), [ticket slicing](https://www.aihero.dev/skills-to-tickets) and [agent-document writing](https://www.aihero.dev/skills-writing-for-agents): small verifiable paths, observable completion criteria and one shared source of rules. The exact checkpoint fields, authority/budget handling and recovery contract are local adaptations, not a Matt-published workflow.

The source of truth is `agent-workbench/shared/workflows/validated-checkpoints.md`. A checked-in project copy records its source revision and local adaptations; source updates and project adoption remain separate actions. Repository delivery guidance continues to own Definition of Done and reporting conventions.
